# Documentation (`resources/docs/`)

Rules for keeping the project documentation in step with the code. The
layout and naming were decided in
[the documentation ADR](adr/20261023-documentation-as-specifications.md).
Frontend rules live in [js/AGENTS.md](../js/AGENTS.md).

```text
resources/docs/
├── adr/<YYYYMMDD>-<slug>.md        one decision per file
├── agents/<topic>.md               agent instructions, indexed by the root AGENTS.md
├── agents/laravel-boost.md         generated by `composer update`; never edit
├── api/<resource>.openapi.yaml     HTTP routes (OpenAPI 3.1)
├── api/<aggregate>.asyncapi.yaml   domain events only (AsyncAPI 3.0)
├── DEPLOYMENT.md                   topology, configuration, CI, deployment
└── ER.md                           Mermaid entity-relationship diagram
```

The starter kit ships the five ADRs in `adr/`
(`20261023-documentation-as-specifications.md`,
`20261104-asyncapi-domain-events-only.md`,
`20261104-docker-compose-environment.md`,
`20261104-tests-against-docker-services.md`, and
`20261104-vuetify-material-design-3.md`), `api/base-app.openapi.yaml`,
`api/base-auth.openapi.yaml`, `api/base-settings.openapi.yaml`,
`DEPLOYMENT.md`, and `ER.md`.

## When to update

Update the documentation in the same commit as the change that requires it:

| Change                                                    | Update                                                     |
| --------------------------------------------------------- | ---------------------------------------------------------- |
| Route added, removed, renamed, or its middleware changed  | `api/<resource>.openapi.yaml`                              |
| Request rules, response status, body, or Inertia props    | `api/<resource>.openapi.yaml`                              |
| Domain event or its listener added, changed, or removed   | `api/<aggregate>.asyncapi.yaml` ([scope](#asyncapi-scope)) |
| Migration                                                 | `ER.md`                                                    |
| Docker, environment variables, drivers, CI, or deploy     | `DEPLOYMENT.md`                                            |
| New aggregate, package, base folder, or changed principle | A new ADR, then the documents it affects                   |

## Resources

- `base-<area>` documents starter-kit routes: `base-app`, `base-auth`, and
  `base-settings`. Keep new framework-integration routes in the matching
  file; add a new `base-<area>` only for a new area. The starter kit has no
  AsyncAPI file because it has no domain events.
- Each aggregate gets `api/<aggregate>.openapi.yaml`, named in kebab-case
  after its `src/` folder (`src/TaskLists` → `task-lists`). When it gets an
  AsyncAPI file is in [AsyncAPI scope](#asyncapi-scope).

## Writing specs

- Verify against the code, not memory:
  `docker compose exec app php artisan route:list --json`, the Request
  `rules()`, the Handler, and the Resource. Never document planned behavior
  as implemented.
- One operation per route. Set `operationId` (camelCase, unique per file),
  `x-route-name` (the Laravel route name), and `x-middleware` (route
  middleware after `web`). Inertia pages add `x-inertia-component` and
  `x-inertia-props`.
- Request bodies mirror `rules()`: required fields, types, and limits.
  Server-owned fields marked `prohibited` stay out of the schema.
- Primary and foreign keys (`id`, `user_id`) only relate rows in the
  database. Routes and responses identify an aggregate root by its `uuid`,
  never its `id`. A child entity under its root uses its own `uuid` when it
  has one, otherwise its numeric `id` (`/tasks/{uuid}/tags/{id}`).
- Response schemas mirror the Resource: the root's `uuid`, public fields, and
  child identifiers as above; never foreign keys. Document each status the
  route really returns, including `302` redirects, `422`, `423`, and `429`.
- Known deviation: two package routes carry numeric ids. Fortify's email
  verification link (`/email/verify/{id}/{hash}`) carries `User.id`, because
  Fortify compares it with the model key and offers no configuration for it.
  The package route `passkey.destroy` (`/user/passkeys/{passkey}`) carries
  the passkey's numeric id. Never copy either pattern into new specs.
- Keep every spec self-contained: define its own `components`; do not
  reference other files.
- AsyncAPI specs follow [AsyncAPI scope](#asyncapi-scope).

## AsyncAPI scope

AsyncAPI documents domain events only: business-level facts that an
aggregate's state changed, named in the past tense (`TaskCompleted`), defined
in `src/{Aggregate}/Events/{Name}.php`, implementing the marker interface
`App\Support\DomainEvent`, and dispatched after the transaction commits
(`ShouldDispatchAfterCommit`). Their listeners live in
`src/{Aggregate}/Listeners/`. The code conventions are in
[architecture](agents/architecture.md#domain-events).

- Never document framework or infrastructure events, even when the
  application listens to them:
    - Laravel and Illuminate events: queue (`JobProcessed`, `JobFailed`,
      `JobQueued`), database (`QueryExecuted`), mail and notifications
      (`MessageSending`, `MessageSent`, `NotificationSent`), cache, session,
      migration, and model lifecycle events such as `eloquent.created`.
    - Authentication events from Laravel or Fortify (`Login`, `Logout`,
      `Registered`, `Verified`, `PasswordReset`, `Lockout`,
      `TwoFactorAuthenticationEnabled`, passkey events).
    - Octane worker events (`RequestReceived`, `WorkerStarting`).
    - Inertia and other package events.
- Listeners and notifications that react to those events, such as Fortify's
  verification email, are framework integration and stay out of AsyncAPI.
- A notification, broadcast, or message published to RabbitMQ appears only as
  an operation of the domain event channel that causes it.
- Channel addresses are the domain event class names; payloads list the
  event's public properties, with sensitive ones marked.
- An aggregate gets `api/<aggregate>.asyncapi.yaml` only when it dispatches or
  listens to domain events.
- `tests/Unit/Docs/AsyncApiScopeTest.php` enforces the scope. Specs are
  `resources/docs/api/*.asyncapi.yaml` or `*.asyncapi.yml` and declare
  `asyncapi: 3.x`. Every address in `channels` and `components.channels` must
  be a class that implements `App\Support\DomainEvent` and
  `Illuminate\Contracts\Events\ShouldDispatchAfterCommit` and lives in
  `src/{Aggregate}/Events/` (any depth below `Events`). Every `DomainEvent`
  class under the `src/` PSR-4 roots must be documented and must live under an
  `Events/` folder.

## ADRs

- File name `<YYYYMMDD>-<slug>.md`, the date of the decision and a
  kebab-case slug.
- Sections: title, `Status` (`proposed`, `accepted`, `superseded by …`),
  `Date`, `Context`, `Decision`, `Consequences`.
- Never rewrite an accepted ADR's decision. Supersede it with a new ADR and
  update the old status line.

## Checks

Parse every YAML spec after editing:

```sh
docker compose exec app php -r 'require "vendor/autoload.php"; foreach (glob("resources/docs/api/*.yaml") as $f) { Symfony\Component\Yaml\Yaml::parseFile($f); echo "ok $f\n"; }'
```

Compare documented routes with the registered ones:

```sh
docker compose exec app php artisan route:list --except-vendor --json
docker compose exec app php artisan route:list --only-vendor --json
```
